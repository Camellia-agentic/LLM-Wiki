# 项目级 Codex 约束

## 回复语言

- 默认使用简体中文回复。
- 代码标识符、文件路径、命令、API 名称、错误原文等保持英文或原文。

## Git 操作

- 不要主动提交 git。
- 只有用户明确要求提交，或明确确认提交后，才可以执行 `git commit`。

## 子智能体调用

- 默认不调用子智能体；由当前智能体直接完成请求。
- 仅当用户明确要求使用子智能体（或并行/独立 agent 处理子任务）时，方可启动 subagent。
- 未经用户明确要求或确认，不得因任务复杂而主动委派子智能体。

## 框架修改规则

涉及框架、目录、模块边界或业务代码组织的修改，统一按简洁的 DDD 分层规则推进。

### 分层结构

- `service`：接口适配层，负责 HTTP/RPC handler、请求参数绑定、响应转换、鉴权上下文传递和调用 `biz`。
- `biz`：业务领域层，负责核心业务规则、用例编排、领域对象、领域接口定义和事务边界设计。
- `data`：数据访问层，负责数据库、对象存储、第三方 SDK、Repository 实现和实体模型转换。

### 依赖方向

- 依赖只能从外向内流动：`service -> biz -> data`。
- `service` 不直接访问数据库、Ent、MinIO、IAM SDK 或其他基础设施实现。
- `biz` 不依赖具体 HTTP 框架，不直接依赖 Gin request/response。
- `biz` 通过接口表达对持久化和外部服务的需求，具体实现放在 `data`。
- `data` 可以依赖 Ent、MinIO、IAM SDK 等基础设施库，但不承载业务规则。

### 目录和文件约束

- 项目文件结构尽量简洁，优先按业务聚合组织代码，避免过早拆出过多包。
- 新增目录必须有明确职责；不要为了形式化 DDD 增加空目录、空接口或单次使用抽象。
- 同一业务能力的 `service`、`biz`、`data` 代码应命名一致，便于追踪调用链。
- 迁移现有代码时采用小步重构，保持接口行为稳定，避免一次性大规模移动无关文件。

### 修改准则

- 优先保持现有功能行为不变，再调整分层边界。
- 每次改动只触碰与目标相关的模块，不做无关格式化和顺手重构。
- 涉及公共业务逻辑时，优先补充或保留可验证的测试命令。
- 如发现现有代码违反分层规则，先在相关任务内局部收敛，不主动扩大改造范围。
