# Claude\-Source

# Claude Code 源码解析：深度复盘总结报告

---

# 1\. 核心结论

Claude Code 不是简单的模型 API 包装器，而是一个围绕大模型构建的**智能体运行时**。底层模型提供推理、代码理解和生成能力，Harness 决定这些能力能否在真实开发环境中：

- 获取正确上下文；

- 选择合适工具；

- 安全地修改系统状态；

- 在长任务中保持目标；

- 处理失败并继续行动；

- 验证结果而非口头宣称完成；

- 在多 Agent 并发时控制冲突；

- 以可观测、可灰度、可回滚的方式迭代。

可以将其抽象为：

```Plaintext
模型能力
  × 上下文质量
  × 工具可控性
  × 反馈闭环
  × 安全可信度
  × 执行稳定性
= 用户实际获得的 Agent 能力
```

这里更接近乘法关系，而非简单加法：任何关键环节接近零，模型能力就难以兑现。

---

# 2\. 整体架构

Claude Code 的核心运行方式可以概括为：**以 TAOR 循环为骨架**

```Plaintext
Think → Act → Observe → Repeat
```

即：

1. **Think**：理解当前目标、历史上下文和环境状态；

2. **Act**：选择工具并提交结构化调用；

3. **Observe**：接收工具结果、错误、测试输出或环境反馈；

4. **Repeat**：判断是否完成；未完成则基于新证据继续行动。

这不是一次性生成代码，而是一个闭环控制过程。

---

## 2\.1 工具调用是唯一的外部行动通道

模型不能直接修改文件或执行命令，一切外部副作用必须经过工具层。

这一层间接性非常关键，因为它使系统可以统一完成：

- 参数 Schema 校验；

- 权限检查；

- 风险分类；

- 路径保护；

- 日志和审计；

- 结果截断与持久化；

- 用户确认；

- 使用量和失败率统计。

因此，工具层不是“模型能力的附属接口”，而是模型与现实环境之间的**控制平面**。

---

## 2\.2 每轮行动都产生上下文成本

每次工具调用及其结果都会进入后续上下文。复杂任务可能包含数十轮调用，因此成本不仅来自模型“思考”，还来自：

- 重复发送系统提示；

- 重复发送历史消息；

- 工具返回内容不断增长；

- 多 Agent 各自维护上下文；

- 长轨迹中的失败尝试和验证信息。

这解释了为什么 Prompt 缓存、延迟工具加载、结果大小控制、微压缩和全量压缩不是边缘优化，而是系统的核心基础设施。

---

## 2\.3 停止条件依赖可验证的任务定义

Agent 通常在不再调用工具、转而输出最终文本时停止。若用户没有定义完成标准，模型可能：

- 过早宣布完成；

- 继续无意义迭代；

- 只完成实现，不完成测试；

- 修复局部症状，却没有验证整体行为。

因此，一个高质量 Agent 任务应显式包含：

```Plaintext
目标是什么
允许修改什么
哪些约束不能违反
用什么方式验证
什么结果算完成
```

“完成标准”本质上是 Agent 的停止条件。

---

# 3\. 技术栈

文档呈现的客户端技术栈包括 Bun、严格模式 TypeScript、React \+ Ink、Zod 和模块懒加载。

|技术|解决的问题|深层意义|
|---|---|---|
|Bun|冷启动、文件 I/O、子进程创建|CLI 的每次启动延迟都直接可感知|
|TypeScript 严格模式|大规模代码库的静态约束|降低跨模块演进中的类型错误|
|React \+ Ink|复杂终端状态管理|终端 UI 与 Web UI 本质上都是响应式状态系统|
|Zod|AI 输出的运行时校验|在概率性模型与确定性程序之间建立边界|
|Lazy Loading|重模块的启动成本|不让低频能力拖慢高频主路径|

其中最值得迁移的认知是：

> AI 返回了“看起来像 JSON 的文本”，不代表程序获得了可信的结构化数据。

TypeScript 只能约束编译期代码，无法保证运行时模型输出。Zod 这样的 Schema 校验承担的是**概率世界到确定性世界的协议转换**。

---

# 4\. System Prompt

Claude Code 的 System Prompt 被拆分为多个模块，覆盖：

- 产品身份；

- 安全边界；

- 工具选择原则；

- 做事方式；

- 风险操作规范；

- 输出风格；

- 验证要求；

- 动态环境信息；

- 项目级配置；

- 记忆和 MCP 信息。

这说明成熟的 Prompt Engineering 已经接近配置与策略工程，而不是单次文案创作。

---

## 4\.1 静态前缀与动态后缀

文档描述了一条明确的动态边界：

```Plaintext
静态、跨用户共享内容
-------------------- 缓存边界
用户、会话和环境相关内容
```

其目的不是语义美观，而是提高 Prompt Cache 命中率。

如果静态前缀中混入多个会话条件，每个条件都会制造新的前缀组合。条件数量增加时，缓存变体可能迅速膨胀，导致：

- 缓存失效；

- 首 token 延迟升高；

- 输入 token 成本显著增加；

- 同一会话内性能不稳定。

因此，Prompt 的物理排列顺序本身就是成本设计：

> **稳定内容靠前，变化内容靠后；高频复用内容进入缓存，易变内容明确隔离。**

---

## 4\.2 Prompt 需要版本适配

文档展示了针对特定模型行为的指令补丁，例如：

- 完成前必须实际验证；

- 测试失败时不得声称通过；

- 未运行验证时必须明确说明；

- 不要通过输出风格掩盖失败；

- 减少无意义注释。

这些指令说明 Harness 不能假设模型是稳定常量。模型升级可能改变：

- 工具调用倾向；

- 诚实性；

- 详细程度；

- 是否过早结束；

- 是否在禁止工具的场景仍尝试调用工具；

- 对相同 Prompt 的遵循程度。

所以，模型升级不是简单替换 API 版本，而应执行：

```Plaintext
模型行为回归测试
→ 识别新失效模式
→ 调整 Prompt、工具约束或运行时策略
→ 灰度发布
→ 监控真实任务指标
```

---

## 4\.3 多种运行模式需要不同身份定义

文档呈现了标准交互、简化嵌入和主动 Agent 等不同 Prompt 路径。这揭示了一项重要原则：

> 不同运行模式不应只是在同一 Prompt 上增删一句话，而应重新定义角色、行动边界、停止条件和交互关系。

交互式编程助手以响应用户为中心；主动 Agent 则需要面对：

- 什么时候主动行动；

- 什么情况应通知用户；

- 长时间后台任务如何管理；

- 如何避免无目标消耗；

- 什么操作必须获得授权。

二者不是同一个产品模式。

---

## 4\.4 定量约束优于模糊形容词

文档提到内部指令使用“工具调用之间不超过一定词数”“最终回复不超过一定词数”等数字化约束，而不是只写“保持简洁”。

这反映出 Prompt 设计的可测量化：

- “简洁”存在巨大解释空间；

- 数字给模型更明确的行为锚点；

- 数字约束可以进行 A/B 测试；

- 最终能关联 token 成本、用户满意度和任务成功率。

不过，数字不应脱离任务复杂度成为死规则，否则会损害解释质量。合理做法是设定默认预算，同时允许复杂任务扩展。

---

# 5\. 工具系统

文档将大量工具归纳为四类原语，构成 Agent 的能力边界：

|原语|作用|风险特征|
|---|---|---|
|Read|获取文件、网页、搜索结果和环境信息|通常低风险，但存在隐私与 Prompt 注入风险|
|Write|创建或修改文件|改变持久状态，需要精确控制|
|Execute|执行 Shell、REPL 或程序|能力最广，风险最高|
|Connect|连接 MCP、Agent 或外部系统|跨越本地边界，涉及认证和数据外发|

这四类原语共同构成 Agent 的“操作系统调用接口”。

---

## 5\.1 专用工具优先，Bash 作为通用后备

Bash 能调用几乎所有开发工具，因此提供了极强的开放世界能力。但它也最难控制：

- 一个命令可能同时读写数据；

- 管道后半段可能引入副作用；

- 重定向、命令替换和 Shell 展开可能隐藏行为；

- 脚本解释器可以执行任意代码；

- 权限系统需要理解整条命令语义。

相比之下，`Read`、`Edit`、`Grep` 等专用工具具有明确的能力边界。权限系统可以根据工具类型快速判断风险。因此正确分层是：

```Plaintext
专用工具：主路径，约束明确、容易审计
Bash：能力逃生舱，覆盖未预见场景
安全解析：约束 Bash 的开放性风险
```

这比“为所有操作只提供一个 Shell”更可靠，也比“完全禁止 Shell”更具泛化能力。

---

## 5\.2 FileEdit：通过协议设计降低模型犯错空间

FileEdit 的关键约束包括：

1. 编辑前必须读取文件；

2. `old_string` 必须唯一匹配；

3. 多处匹配默认拒绝，除非明确指定全量替换；

4. 文件在读取后若发生变化，要求重新读取；

5. 使用精确字符串，而不是让模型生成复杂正则。

这体现了一种核心思想：

> 不要仅要求模型“编辑得更小心”，而要让错误编辑在协议层难以发生。

其背后是典型的乐观并发控制：

```Plaintext
读取当前状态
→ 基于该状态生成变更
→ 提交前验证状态未改变
→ 精确应用变更
```

AI 工具设计优秀程度，很大程度上取决于是否能把模型容易犯的错误转化为可检测的协议失败。

---

## 5\.3 工具结果需要分层可见，而不是直接截断

当工具输出过大时，文档描述的策略是：

```Plaintext
完整结果保存到磁盘
→ 上下文只注入摘要、预览和文件路径
→ 模型需要时再按范围读取
```

这实现了“存储”和“上下文可见性”的分离：

- 数据不会丢失；

- 不让一次工具调用占满上下文；

- 模型可按需逐步展开；

- 后续可重新检查原始结果。

因此，上下文窗口不应被视为日志仓库，而应被视为**工作内存**。完整数据可以存在外部介质中，上下文只保留当前决策所需的信息。

---

## 5\.4 Deferred Tools：工具本身也有认知成本

每个工具都需要向模型提供：

- 名称；

- 功能说明；

- 参数 Schema；

- 使用限制；

- 示例或注意事项。

工具越多，System Prompt 越长，模型选择难度也越大。MCP 可能进一步暴露大量工具，导致上下文被工具说明占据。

延迟加载机制的逻辑是：

```Plaintext
初始只暴露工具索引
→ 模型判断需要某类能力
→ 查询并加载具体工具定义
→ 再调用工具
```

它解决的不只是 token 成本，还包括工具选择中的注意力稀释。

> 工具数量不是能力的线性增益。工具越多，若缺乏发现和路由机制，模型越可能选错工具。

---

# 6\. 权限系统

文档呈现的权限模式大致包括：

- 交互确认；

- 自动分类；

- 绕过权限。

其中 Auto 模式并非无条件放行，而是将确定性规则与模型判断组合为分层流水线。

---

## 6\.1 四层审查：把复杂判断留给少数情况

权限判断流程可概括为：

```Plaintext
用户规则匹配
→ 明显低风险操作快速通过
→ 只读工具白名单
→ 独立模型进行风险分类
```

其设计目标是同时优化：

- **安全性**：复杂操作进入语义审查；

- **延迟**：简单操作不调用额外模型；

- **成本**：大部分请求由规则处理；

- **可解释性**：风险判断可以生成理由。

这是一种通用的级联架构：

> 便宜、确定的规则处理大多数简单样本；昂贵、智能的模型只处理规则无法判断的尾部样本。

---

## 6\.2 两阶段安全分类器

对于进入模型分类的操作，文档描述了两阶段预算：

1. 小 token 预算完成快速判断；

2. 只有可疑操作进入大预算深度分析。

安全模型使用低温度，以追求稳定性而非创造性。它与主任务 Agent 分离，因为二者目标不同：

- 主 Agent 追求完成任务；

- 安全 Agent 追求识别风险。

如果让执行者自己判断自己的行为是否安全，会存在目标冲突：执行者天然倾向于让行动继续。

---

## 6\.3 熔断与降级比追求完美分类器更现实

分类器可能误判。如果连续拒绝导致主 Agent 不断重试，系统会陷入：

```Plaintext
提出操作
→ 被分类器拒绝
→ 换一种表达重试
→ 再次拒绝
→ 无限循环
```

文档中的熔断机制会在连续或累计拒绝达到阈值后，降级为人工确认。

这体现了可靠系统的重要原则：

> 不要假设智能组件永不出错；要提前设计错误发生后的可恢复路径。

安全模型不是系统最终权威，必要时应把决策权交回用户。

---

## 6\.4 保护持久化攻击面

Shell 配置、Git 全局配置、Agent 自身配置和 MCP 配置具有跨会话影响。一旦被恶意修改，危害可能在未来持续存在。

因此，风险分类不应只按“写文件”统一处理，而应考虑：

- 作用域：临时、项目级、用户级还是系统级；

- 可逆性：能否轻易回滚；

- 持久性：是否跨会话生效；

- 外部影响：是否触发网络、部署或代码推送；

- 权限扩张：是否改变后续 Agent 的权限。

可以将风险理解为：

```Plaintext
风险 ≈ 副作用范围 × 持续时间 × 不可逆性 × 权限扩张能力
```

---

## 6\.5 自动模式必须重新解释用户授权

用户在手动模式中配置“允许所有 Bash”时，仍可能依赖每次可见的确认过程；进入无人值守的自动模式后，同一规则的风险发生了变化。

文档所述方案会在 Auto 模式中临时剥离过宽权限，退出后恢复。这体现出：

> 授权的含义依赖运行模式。人类在环和无人值守不是相同的安全环境。

因此，权限规则不应只看静态配置，还要看：

- 当前是否有用户监督；

- 任务来自谁；

- 是否在可信项目中；

- 是否涉及外部系统；

- 操作能否自动恢复。

---

## 6\.6 权限弹窗应支持“知情决策”

一个只有“允许/拒绝”的弹窗会造成确认疲劳。更合理的界面应告诉用户：

- 操作要做什么；

- Agent 为什么需要做；

- 可能产生什么风险；

- 风险等级；

- 影响是否可恢复。

权限 UX 是安全架构的一部分。若解释太长，用户不会读；若完全不解释，用户只能盲目授权。结构化、短文本风险说明是在信息量与决策速度之间取得平衡。

---

# 7\. 记忆系统

文档呈现的记忆系统非常克制：以 Markdown 文件和目录作为物理存储，而不是使用向量数据库。记忆大致分为：

|类型|内容|变化速度|
|---|---|---|
|User|身份、角色、长期偏好|慢|
|Feedback|对 Agent 行为的纠正与认可|中慢|
|Project|项目目标、状态、期限|较快|
|Reference|外部系统及资源入口|中慢|

---

## 7\.1 核心原则：记忆是历史观察，不是实时真相

文档强调不应长期保存：

- 文件位置；

- 代码结构；

- 函数行号；

- Git 历史；

- 临时修复方案；

- 易变化的任务细节；

- 已存在于项目说明中的内容。

原因在于，代码状态变化快。错误的持久记忆比没有记忆更危险，因为它会让模型带着错误先验行动。因此，记忆与搜索的职责应明确分开：

```Plaintext
记忆：提供稳定偏好、历史判断和检索线索
搜索：获取当前代码、文件位置和最新事实
验证：将历史线索与当前状态对照
```

这是整份文档中最具迁移性的设计之一：

> **持久化变化慢的信息；实时读取变化快的信息。**

---

## 7\.2 记忆入口必须有硬性预算

索引文件设置行数和字节上限，原因是它会进入每次会话的 Prompt。若没有上限，记忆会持续增长，最终带来：

- 上下文挤占；

- 召回噪声；

- 冲突增加；

- Prompt 缓存成本上升；

- 模型注意力被低价值信息稀释。

硬上限迫使系统执行取舍。成熟记忆系统的目标不是“从不遗忘”，而是：

> 在固定可见预算中保留未来效用最高的信息。

---

## 7\.3 索引与正文分离

`MEMORY.md` 更像索引，而详细内容保存在单独文件中。其效果是：

- 每轮只暴露少量摘要；

- 相关记忆可以按需加载；

- 用户可直接检查和修改；

- 记忆条目具有明确类型和描述；

- 总容量可以大于常驻上下文容量。

这与虚拟内存的思路相似：常驻的是索引和高频信息，完整内容按需分页载入。

---

## 7\.4 独立记忆提取 Agent

记忆提取交给独立 Agent，可以实现：

### 上下文隔离

提取过程中的分析不会污染主任务上下文。

### 权限最小化

提取 Agent 只获得读取会话和写入记忆目录的权限，减少 Prompt 注入形成持久化攻击的风险。

### 主任务解耦

主 Agent 专注交付，提取 Agent 专注判断“什么值得跨会话保存”。

### 缓存复用

保持 System Prompt、工具列表和模型一致，通过运行时钩子限制权限，从而避免破坏 Prompt Cache。

这说明安全隔离不一定要求改变模型可见接口；也可以保持接口稳定，在执行时实施能力控制。

---

## 7\.5 记忆需要年龄、验证与巩固机制

旧记忆应附带陈旧提示，提醒模型在引用代码事实前读取当前状态。后台整理过程则负责：

- 收集近期会话信号；

- 合并重复记忆；

- 将相对时间转为绝对时间；

- 删除过时信息；

- 更新索引；

- 控制入口预算。

这说明记忆不是简单写入，而是完整生命周期：

```Plaintext
提取 → 分类 → 索引 → 召回 → 验证 → 合并 → 淘汰
```

此外，记忆不仅应记录用户否定，也应记录明确认可。若只保存失败和纠正，Agent 可能逐渐变得过度保守；保存成功偏好能帮助它稳定复用被认可的行为。

---

# 8\. 上下文管理

长对话一定会超出上下文预算，因此压缩本质上不可避免。关键问题不是“能否无损压缩”，而是：

> 哪些信息必须原样保留，哪些可以总结，哪些可以重新获取，哪些应该被丢弃？

> 【不是避免遗忘，而是设计如何遗忘】

---

## 8\.1 多层压缩策略

文档呈现的压缩方式包括：

|压缩类型|处理对象|目的|
|---|---|---|
|Micro Compact|旧工具结果|持续清理低价值大块内容|
|Partial Compact|部分对话区段|平衡原文保留与缓存复用|
|Full Compact|完整历史|在接近窗口上限时重建上下文|
|Reactive Compact|超限错误后的恢复|失败兜底|

合理顺序应是先做局部清理，再做全量摘要：

```Plaintext
增量清理低价值工具输出
→ 部分压缩历史
→ 必要时全量结构化压缩
→ 超限时反应式恢复
```

这类似于内存管理中的分代回收：优先清理体积大、重建成本低、长期价值低的信息。

---

## 8\.2 九段式结构化压缩

文档所述压缩模板保留：

1. 用户主要请求和意图；

2. 关键技术概念；

3. 文件与代码修改；

4. 错误与修复；

5. 问题解决过程；

6. 全部用户消息；

7. 待完成任务；

8. 当前正在进行的工作；

9. 与最近请求一致的下一步。

它比自由摘要更可靠，因为它显式定义了信息保留策略。

---

## 8\.3 用户消息具有最高保留优先级

工具结果通常可以重新运行，代码可以重新读取，但用户消息包含：

- 目标；

- 偏好；

- 否定；

- 范围约束；

- 风险容忍度；

- 需求变化；

- 对前一结果的纠正。

丢失工具输出意味着多花一次查询；丢失用户约束意味着 Agent 可能完成错误任务。因此：

> 用户消息不是普通上下文，而是任务规范和对齐信号。

---

## 8\.4 防止任务漂移需要原文锚点

压缩是一次语义重写，多次压缩会产生累积误差。为避免摘要逐渐偏离原始请求，文档要求对当前任务和下一步保留用户原文引用。这是一个重要认识：

```Plaintext
摘要 → 摘要的摘要 → 更短摘要
```

会像多轮转述一样逐渐丢失细微约束。原文引用提供了不可再解释的锚点。

因此，面向长期任务的状态记录，最好同时保留：

- 结构化摘要；

- 当前目标的原始文本；

- 验收标准原文；

- 最近一次用户纠正原文；

- 尚未完成事项。

---

## 8\.5 上下文中的信息应按“可重建性”排序

一种通用优先级如下：

|信息|重建难度|保留优先级|
|---|---|---|
|用户意图与约束|很高|最高|
|当前工作状态|高|很高|
|未完成任务|高|很高|
|已做出的设计决策及原因|中高|高|
|失败方案及失败原因|中|高|
|文件路径和代码定位|中低|中|
|原始工具大输出|低，可重跑|低|
|重复文件内容|很低|最低|

上下文管理的核心不是按时间机械截断，而是按未来决策价值和可重建成本进行压缩。

---

# 9\. 搜索系统

文档最反直觉的结论是：源码中未发现代码向量数据库或 Embedding 检索，而主要使用：

```Plaintext
Glob 发现文件
→ Grep 定位符号和位置
→ Read 精确读取相关区段
→ 模型理解结果并迭代搜索
```

---

## 9\.1 简单检索成立的条件

Grep 路线有效，不意味着 RAG 普遍无用。它成立需要若干条件：

1. **代码具有丰富的精确标识符**
函数名、类型名、错误信息和配置键都适合文本搜索。

2. **模型能够制定迭代搜索策略**
模型可根据一次结果生成下一组关键词。

3. **代码库能被本地高效扫描**
ripgrep 对中小型本地仓库速度极高。

4. **数据必须实时一致**
代码变化频繁，实时扫描不会遭遇索引陈旧。

5. **检索结果由 LLM 消费**
原始匹配结果不必直接满足人类阅读体验，模型会进行二次理解。

6. **上下文和工具调用预算足够**
系统可以通过多轮搜索弥补单次召回不足。

---

## 9\.2 Grep 相比代码 RAG 的优势

- 结果精确且可解释；

- 无需构建索引；

- 打开项目即可使用；

- 代码变化后立即生效；

- 不依赖 Chunk 划分；

- 不存在 Embedding 模型升级后的重建成本；

- 能自然匹配文件名、符号、日志和错误字符串。

代码 RAG 的典型风险包括：

- Chunk 切断函数或调用关系；

- 语义相似但功能无关；

- 索引与工作区不一致；

- 新文件尚未进入索引；

- Embedding 无法可靠表示动态依赖；

- 检索排序不可解释。

---

## 9\.3 搜索工具本身仍经过精细设计

“不用 RAG”不等于“直接裸用 grep”。文档中的工具层进行了大量优化：

- 默认先返回文件列表，控制信息量；

- 支持匹配内容、文件列表和计数三种模式；

- 支持上下文行、文件类型和 Glob 过滤；

- 默认限制结果数量；

- 约束单行最大长度；

- 排除版本控制目录；

- 将绝对路径转为相对路径以节省 token；

- 支持 offset 和 limit 分页；

- 文件未变化时避免重复返回全部内容；

- Read 可读取代码、PDF、图片和 Notebook。

真正有效的不是单独的 grep，而是：

> **高性能精确检索 \+ 受控输出协议 \+ 强模型的多轮策略搜索。**

---

## 9\.4 “Grep 胜过 RAG”的边界

该结论不应泛化为所有知识检索场景。以下情况仍可能需要 RAG、符号索引或混合检索：

- 超大规模跨仓库代码；

- 查询主要是业务概念而非代码标识符；

- 需要跨语言、跨模态语义召回；

- 历史文档与代码联合检索；

- 低延迟要求不允许多轮搜索；

- 模型较弱，无法制定高质量关键词；

- 需要全局调用图或类型关系；

- 搜索结果直接面向用户，而不是由强模型继续处理。

更准确的原则是：

> 默认从最简单、实时、可解释的检索开始；只有在实际召回瓶颈被测量出来后，再引入向量或结构化索引。

---

# 10\. 多 Agent

文档中的多 Agent 系统采用 Team、Leader、Teammate 层级，并支持独立执行环境、邮箱通信、权限冒泡和验证阶段。

---

## 10\.1 多 Agent 的正确价值

多 Agent 适合：

- 可独立并行的代码调研；

- 多模块实现；

- 执行与验证分离；

- 不同方案并行探索；

- 大型任务的信息搜集和汇总。

不适合：

- 强顺序依赖的小任务；

- 需要频繁共享细粒度状态的修改；

- 单 Agent 已能低成本完成的简单问答；

- 拆分成本高于执行成本的任务。

并行 Agent 的收益应考虑：

```Plaintext
净收益
= 并行缩短的时间
- 任务拆分成本
- 上下文复制成本
- 协调通信成本
- 冲突合并成本
- 重复探索成本
```

---

## 10\.2 Git Worktree：用空间隔离换取冲突可控

多个 Agent 在同一工作区并发修改极易互相覆盖。Git Worktree 让每个 Agent 拥有独立工作目录和分支，最终通过 Git 合并。

其优势包括：

- 并发修改不会直接覆盖；

- 每个 Agent 可以独立测试；

- 失败任务容易丢弃；

- 修改范围可审计；

- 合并冲突延迟到明确阶段处理。

这体现了并发系统的经典原则：

> 与其依赖所有 Agent 自觉避免冲突，不如通过环境隔离从机制上消除共享写入。

---

## 10\.3 Worker Prompt 必须自包含

Worker 不共享 Coordinator 的全部对话，这虽然增加了委派 Prompt 的编写责任，却能避免：

- 每个 Worker 重复加载完整历史；

- 无关探索噪声相互污染；

- Worker 误解其他任务信息；

- 上下文成本随 Agent 数量线性膨胀。

自包含委派至少应明确：

```Plaintext
任务目标
相关文件与定位
允许修改范围
禁止事项
已有调查结论
预期输出
验证方法
完成标准
```

多 Agent 系统的主要失败往往不是模型不够强，而是委派规格不足。

---

## 10\.4 Coordinator 不应只是消息转发器

Coordinator 的职责包括：

- 判断是否值得委派；

- 将用户目标分解为独立任务；

- 理解 Worker 返回的信息；

- 汇总冲突结论；

- 生成统一实现规格；

- 管理权限请求；

- 决定继续原 Worker 还是启动新 Worker；

- 面向用户输出整合后的结果。

如果 Coordinator 只是把 Worker A 的结果原样转给 Worker B，系统就失去了真正的协调层。有效协调需要压缩、判断和重新表达信息。

---

## 10\.5 执行者与验证者分离

独立 Verification Agent 的价值在于减少自我确认偏差：

- 执行 Agent 已对自己的方案形成认知锚定；

- 它可能把“代码存在”误认为“功能成立”；

- 它可能选择对自己方案有利的测试；

- 它可能忽略未覆盖的边界情况。

验证者需要重新运行测试、检查类型错误和边界条件，并输出明确状态，例如 `PASS / FAIL / PARTIAL`。

> 验证不是阅读实现，而是产生支持“它确实工作”的独立证据。

---

## 10\.6 生命周期管理是多 Agent 的基本工程

团队创建之外，还必须处理：

- 子进程终止；

- Worktree 清理；

- 临时目录删除；

- 权限请求过期；

- 文件锁释放；

- 异常退出；

- 孤儿进程；

- 重复清理。

合理顺序通常是：

```Plaintext
停止活动进程
→ 释放运行时资源
→ 清理工作区
→ 删除元数据
→ 更新 UI 和任务状态
```

多 Agent 原型很容易展示“多个模型同时输出”，但产品级系统的难点在资源所有权和异常恢复。

---

# 11\. Feature Flags

文档描述了大量运行时 Feature Flag，以及编译时内部/外部代码隔离。

AI 产品比传统软件更需要 Flag，因为最终行为同时依赖：

- 应用代码；

- 模型版本；

- System Prompt；

- 工具描述；

- 权限策略；

- 上下文压缩方式；

- 用户类型；

- 推理预算；

- 实验功能组合。

任何一个因素变化都可能引发非局部行为变化。

---

## 11\.1 运行时 Flag 的价值

- 按平台、组织、订阅等级灰度；

- A/B 测试 Prompt 和行为策略；

- 不重新部署即可关闭问题功能；

- 记录用户实际曝光，而不只是配置分组；

- 通过磁盘缓存应对远程服务不可用；

- 为内部员工提供覆写能力。

真正的实验指标不应只看是否启用，还要看：

- 任务成功率；

- 用户纠正次数；

- 权限拒绝率；

- 工具调用数量；

- token 和延迟；

- 测试通过率；

- 回退率；

- 用户负面反馈。

---

## 11\.2 编译时隔离优于运行时隐藏

运行时 `if` 只能保证代码通常不执行，无法保证：

- 代码不会被反编译；

- 敏感字符串不会出现在包中；

- 隐藏功能无法被错误触发；

- 内部依赖不会扩大攻击面。

通过构建常量和 Dead Code Elimination，外部包可以物理移除内部模块。这同时减少：

- 包体积；

- 启动成本；

- 敏感信息暴露；

- 潜在漏洞面。

原则是：

```Plaintext
灰度实验：运行时 Flag
敏感能力隔离：编译时 Gate
权限控制：运行时鉴权
```

三者解决的是不同问题，不能互相替代。

---

# 12\. 内部版与外部版

文档认为内部版采用了更严格的行为标准，例如：

- 不粉饰测试失败；

- 未运行验证时明确说明；

- 完成前必须实际验证；

- 默认不添加解释“代码做什么”的冗余注释；

- 面向用户写自然、可理解的文字；

- 使用定量长度约束；

- 复杂实现后引入独立验证。

这些规则共同指向一种成熟的 Agent 交付标准：

```Plaintext
事实忠实
> 表面自信

可验证结果
> 口头承诺

必要解释
> 输出堆积

独立证据
> 自我评价
```

不过，文档涉及内部代号、反蒸馏和隐蔽模式的部分包含作者解释及伦理判断，应与可复用工程原则分开看待。尤其是隐藏 AI 参与痕迹，会涉及开源社区透明度、贡献归属和组织政策问题，不能仅当作技术优化。

---

# 13\. Harness Engineering 

Prompt Engineering 只回答“模型应如何理解和表达”；Harness Engineering 还必须回答：

|层级|核心问题|
|---|---|
|Prompt|模型是谁，应遵循什么规则？|
|Context|当前决策需要看到什么？|
|Retrieval|如何获取最新且相关的信息？|
|Tools|模型可以采取哪些行动？|
|Permissions|哪些行动可自动执行，哪些需审批？|
|Memory|什么值得跨会话保存？|
|Verification|如何证明任务真的完成？|
|Multi\-Agent|如何分工、隔离、通信和合并？|
|Observability|如何知道系统为什么成功或失败？|
|Experimentation|如何灰度、对比和回滚行为变化？|

因此，Harness 可以被理解为大模型的：

- 运行时；

- 能力控制器；

- 工作内存系统；

- 安全内核；

- 反馈通道；

- 产品化外壳。

---

# 14\. 十条高密度设计原则

## 原则 1：复杂度应集中，而不是平均分散

当模型已经具备强理解能力时，外围组件优先采用可解释、低运维的方案。复杂度只有在被实际瓶颈证明必要时才增加。

---

## 原则 2：工具协议比 Prompt 劝告更可靠

“请小心修改文件”不如“未读文件不得修改、旧文本必须唯一匹配、状态变化后必须重读”。

Prompt 约束是软约束；Schema、权限和状态机是硬约束。

---

## 原则 3：安全是自治能力的许可证

没有可信权限系统，用户不会允许 Agent 自动执行高价值任务。安全投入不是减少能力，而是扩大用户愿意授予的能力范围。

---

## 原则 4：持久记忆只保存低变化、高复用信息

偏好、长期约束和稳定判断适合保存；代码位置和实时事实应重新检索。记忆是线索，不是权威真相。

---

## 原则 5：上下文是工作内存，不是数据仓库

原始大结果放外部存储，上下文只保留索引、摘要和当前决策所需片段。先增量清理，再全量压缩。

---

## 原则 6：压缩一定有损，必须显式定义损失策略

优先保护用户意图、当前任务和待办事项；优先清除可重新查询的工具结果。用原文锚点抑制多轮摘要产生的任务漂移。

---

## 原则 7：搜索策略可能比搜索算法更重要

强模型可以通过多轮 Glob、Grep 和 Read 迭代逼近目标。应先评估模型是否能补偿简单检索，再决定是否引入 RAG。

---

## 原则 8：多 Agent 的关键是隔离、规格和验收

增加 Agent 数量不会自动增加正确性。有效系统需要清晰的任务边界、独立工作区、自包含 Prompt、结果合并和独立验证。

---

## 原则 9：缓存结构属于产品架构

静态前缀、动态后缀、延迟工具加载、缓存 TTL 稳定性和部分压缩，会直接影响成本与延迟。Prompt 内容与缓存布局必须联合设计。

---

## 原则 10：AI 产品必须可实验、可观测、可回滚

模型行为具有概率性，单靠代码 Review 无法预测真实效果。每项行为变化都应支持灰度发布、曝光记录、指标监控和快速回退。

---

# 15\. 批判性修正

## 15\.1 “Grep 打败 RAG”是条件性结论

更准确的表述是：

> 在本地、实时变化、标识符丰富的代码库中，强模型配合迭代式精确搜索，可能比预构建向量索引具有更好的整体成本、时效性和可解释性。

它不能证明向量检索在企业知识库、跨仓库检索或自然语言概念搜索中没有价值。

---

## 15\.2 “只记偏好，不记代码”也不是绝对规则

某些代码知识仍可能适合持久化，例如：

- 稳定架构决策；

- 经人工确认的项目约束；

- 跨会话不易从代码直接恢复的设计原因；

- 外部依赖的业务语义；

- 关键安全不变量。

关键不是“代码信息一律不记”，而是评估：

```Plaintext
变化速度
× 重新获取成本
× 错误记忆危害
× 未来复用价值
```

变化快、易重查、错误代价高的信息不应长期保存。

---

## 15\.3 文件系统方案简单，但有规模与一致性边界

Markdown 和邮箱文件具有透明、易调试、低运维的优势，但在以下场景可能不足：

- 多设备实时同步；

- 大规模并发写入；

- 细粒度权限；

- 复杂事务；

- 全文统计分析；

- 企业级审计；

- 海量记忆召回。

“简单优先”不等于“永远拒绝数据库”，而是先用最小系统验证需求，再根据真实瓶颈升级。

---

## 15\.4 Harness 无法替代模型能力

Harness 可以：

- 降低错误率；

- 提高正确上下文获取概率；

- 限制危险行为；

- 强制验证；

- 改善成本和交互体验。

但它不能完全弥补：

- 基础推理不足；

- 长程规划能力弱；

- 代码语义理解错误；

- 模型无法识别关键线索；

- 对未知技术栈缺乏知识。

最优系统不是弱模型加复杂 Harness，也不是强模型加薄包装，而是让两者边界匹配。

# 16\.  AI Coding Agent 推荐落地

## 第一阶段：最小可信闭环

```Plaintext
TAOR 循环
+ Read / Grep / Glob / Edit / Bash
+ 严格 Schema
+ 用户确认
+ 测试验证
```

先确保 Agent 能观察、行动、获取反馈并证明结果。

---

## 第二阶段：增加硬约束

```Plaintext
编辑前必须读取
+ 唯一匹配修改
+ 文件版本检查
+ 受保护路径
+ Bash 语义分析
+ 大结果外部持久化
```

优先通过协议和运行时约束降低错误，而不是继续堆 Prompt。

---

## 第三阶段：控制成本和上下文

```Plaintext
静态/动态 Prompt 分区
+ Prompt Cache
+ Deferred Tools
+ 工具结果分页
+ Micro Compact
+ 结构化 Full Compact
```

此阶段的目标是让长任务成本可控、行为不漂移。

---

## 第四阶段：建立有限记忆

```Plaintext
稳定偏好存储
+ 类型化记忆
+ 入口预算
+ 独立提取 Agent
+ 年龄提示
+ 使用前验证
+ 周期性合并与清理
```

不要一开始就追求“记住所有内容”。

---

## 第五阶段：提高自治与安全

```Plaintext
规则白名单
+ 风险分类器
+ 两阶段审查
+ 熔断降级
+ 权限解释
+ 模式相关授权
+ 审计日志
```

只有安全系统成熟后，才应扩大 Auto 模式范围。

---

## 第六阶段：多 Agent 与产品实验

```Plaintext
任务分解
+ Worktree 隔离
+ 自包含 Worker Prompt
+ Coordinator 汇总
+ 独立 Verification
+ Feature Flags
+ 行为指标与回滚
```

多 Agent 应是单 Agent 系统成熟后的扩展，而不是掩盖基础闭环缺陷的手段。

# 18\. 总结

这份源码解析最重要的启示，不是“Claude Code 使用了哪些具体库”，也不是复制某个 Prompt，而是理解成熟 Agent 产品的基本范式：

> **模型负责理解、推理与生成；Harness 负责提供正确状态、限定行动空间、管理上下文、控制风险、验证结果并维持长期运行。**

Claude Code 所体现的工程哲学可以浓缩为：

```Plaintext
用简单、实时、可解释的组件提供原始能力；
用强模型承担高层理解和策略决策；
用工具协议把软要求转化为硬边界；
用分层权限把自治建立在可信基础上；
用有限记忆保存稳定信息，而不是囤积动态事实；
用结构化压缩主动决定遗忘什么；
用隔离和独立验证管理多 Agent；
用缓存、灰度与回滚把概率性模型变成可运营产品。
```

最终，Harness Engineering 的本质不是给模型增加更多包装，而是解决一个更现实的问题：

> **如何让一个能力强但概率性、可能犯错的模型，在真实软件环境中持续做出可控、可验证、可恢复且值得信任的行动。**
